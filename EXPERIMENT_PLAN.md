# План кода: бенчмарк методов оптимизации инференса

План реализации экспериментальной части. Текст ВКР — отдельно, здесь не рассматривается.

## 0. Рамки
- **Цель кода:** измерить **влияние методов оптимизации на инференс** (скорость, память, где надо — качество) → сделать выводы. Рекомендации «какой метод в каком сценарии» — следствие выводов, не самоцель.
- **База кода:** строим от `rollback-pr2` (простые явные скрипты). `main` на 4 PR впереди, но ушёл «не туда» по фокусу/методам — берём оттуда только проверенные **механики** референсом (см. §8), структуру пакета `src/llm_inference` целиком не тащим.
- **Структура исследования — по методам, а не одна общая матрица.** Бейзлайн → дальше каждый метод отдельным сюжетом, в сравнении с бейзлайном. Большая сводная таблица не нужна; важны графики «где метод даёт прирост».
- **Железо:** один RTX 3090 24GB (Ampere, SM 8.6).
  - *Физически нельзя:* тензорный/конвейерный параллелизм (нужно ≥2 GPU).
  - *Исключаем по выбору (не по железу):* vLLM, TensorRT-LLM — на 3090 запускаются, но это серверные фреймворки другого уровня (PagedAttention, continuous batching, свои ядра). Харнесс намеренно на чистом HF — чтобы сравнивать «яблоки к яблокам». Их даём обзором в тексте.
  - *Caveat железа:* FP8 на Ampere не ускоряет (нет FP8-ядер) — только упомянуть.
- **Время:** дедлайн 10 июня → компут минимизируем, тяжёлый прогон на ночь.
- **Базовая точность:** dtype `auto` у Qwen → **bf16** (не fp16). Это fp-референс для всех сравнений.

## 1. Модели
- **Отладка:** `Qwen2.5-1.5B-Instruct` (уже скачана) — проверить код-пути, не полная матрица.
- **Основная:** `Qwen2.5-7B-Instruct` (~15GB) + draft `Qwen2.5-0.5B-Instruct` (~1GB) для спек-декодинга (одно семейство → совместимый токенизатор).
- AWQ/GPTQ требуют **готовых квантованных чекпойнтов** (мы не калибруем). Для 7B есть; для 1.5B — проверить, иначе на 1.5B отлаживаем только bnb.

## 2. Дизайн по методам
Принципы: (1) меряем только оси, на которые метод влияет; (2) **качество — только для lossy-методов (квант)**; lossless (кэш, спек) → только скорость/память (+ для спека fidelity-чек); (3) **батч варьируем только там, где есть к нему чувствительность**.

**0. Бейзлайн** — базовые метрики (TTFT, tok/s, ms/токен, VRAM). Точка отсчёта.

**1. KV-cache** (lossless, без качества):
- cache off vs on → прирост tok/s, рост VRAM.
- **batch-sweep {1,4,16}** → throughput↑ и VRAM↑ (основной батч-сюжет).
- размер KV-кэша по длине (из [manual_kv_loop.py](scripts/manual_kv_loop.py)).

**2. Квантизация** (lossy → качество обязательно):
- {fp16, bnb-int8, bnb-int4, AWQ-int4, GPTQ-int4}: скорость + VRAM по типам.
- **качество** по тем же вариантам (MMLU/GSM8K/perplexity) — единственное место с качеством.
- batch-sweep (экономно): int4, AWQ × {4,16} — memory-headroom.
- Ожидаемо: bnb = память, не скорость; INT8 часто медленнее; AWQ/GPTQ (Marlin) быстрее fp16. Контраст bnb↔AWQ — главный вывод.

**3. Спекулятивный декодинг** (lossless, без качества, только draft-модель):
- 0.5B draft → target: speedup vs бейзлайн, **acceptance rate**, effective tok/s.
- режим **batch=1** (latency-метод; на больших батчах выигрыш тает — отметим).
- fidelity-чек: выход == greedy target (заодно проверка корректности).

**4. Комбинации** (складываются ли выигрыши): `int4+spec`, `AWQ+spec`, batch=1.

## 3. Метрики
**Производительность (разбивка по фазам — roofline):** TTFT (prefill), ms/токен / TPOT (decode), throughput tok/s, total latency, peak VRAM. Спек дополнительно: acceptance rate, effective tok/s.
**Качество (только квант, только 7B):** MMLU ~500 (логпробы, без генерации), GSM8K-CoT ~300 (генерация), perplexity (WikiText-2).
**Fidelity к fp16:** только санити-чек спек-декодинга, не метрика качества.

## 4. Архитектура кода (зафиксировано)
- **Единый раннер** `scripts/benchmark.py`, флаги `--quant {none,int8,int4,awq,gptq}`, `--draft-model`, `--no-cache`, `--batch-size`, `--repeats`, `--fixed-length`. Все speed-конфиги — одним путём через `generate()`. Общие хелперы — в общий модуль (расширяем [summary.py](scripts/summary.py) / новый `bench_core.py`).
- [manual_kv_loop.py](scripts/manual_kv_loop.py) **оставляем** — артефакт милстоуна «ручной KV-cache», источник размера кэша, кросс-валидация чисел `fp16 cache` из `generate()`.
- **Процесс на конфиг.** Драйвер `scripts/run_matrix.py` запускает каждый конфиг отдельным процессом → чистый `max_memory_allocated()`, нет фрагментации/OOM. Каждый процесс пишет свой summary JSON.
- **Инкрементальность / добор.** Агрегатор читает те summary, что есть в `results/`. Пропуски (точки батча, quality для 1.5B) добираются позже **без перепрогона** — дописать JSON, пере-агрегировать. *Quality-добор безопасен всегда (детерминирован); latency-добор лучше в той же сессии (клоки/температура), дрейф ловим логом temp/clock.*
- **Fixed-length** для speed (`min_new_tokens=max_new_tokens`, игнор EOS) → идентичная работа во всех конфигах и чистый батч (нет рваных хвостов). Quality-трек — естественная остановка.
- **Повторы:** 3 прохода; на промпт медиана по повторам; ± = шум по повторам.
- **no-cache** полноценно только на 1.5B; на 7B — 10 промптов × 1 (квадратичный, иначе часы).
- **Спек — правка стримера:** `assistant_model` отдаёт токены блоками → записываем длину блока → acceptance rate + effective tok/s; TTFT = время до первого блока.
- **Батч:** static batching = **left-padding** + attention_mask. Потокенный CUDA-стример при batch>1 не работает → меряем агрегатный throughput + VRAM (без потокенных перцентилей). Continuous batching (vLLM) — вне кода, в текст.
- **Квант:** bnb с `bnb_4bit_compute_dtype=bfloat16`, nf4, double-quant; AWQ/GPTQ — готовые чекпойнты.
- **Дамп текста** генерации — для fidelity и примеров. **Метаданные:** git_commit, temp/clock GPU.

## 5. Трек качества (отдельно от speed)
- `scripts/eval_quality.py`. **Primary: `lm-evaluation-harness`**; **fallback** при конфликте с transformers 5.8 — свой мини-эвалюатор (MMLU логпробами, GSM8K генерация+regex) или отдельный venv. *(дефолт можно пересмотреть)*
- Только 7B, конфиги {fp16, int8, int4, AWQ, GPTQ}. MMLU `--limit 500`, GSM8K-CoT `--limit ~300`. Quality для 1.5B — опционально, добором.

## 6. Артефакты
- Per-config summary JSON + **агрегатор** `scripts/aggregate.py` (читает доступные summary).
- `scripts/plots.py` → **графики по методам**: speedup/VRAM кэша vs батч; скорость+VRAM+качество по типам кванта; acceptance/speedup спека. Pareto скорость↔качество и скорость↔VRAM по кванту.
- Матрица «метод → сценарий» как итог выводов.

## 7. Счёт конфигов
**Speed на 7B (~15):** кэш 4 (no-cache + {1,4,16}) · квант b=1: 4 · квант batch-sweep: 4 · спек: 1 · комбо: 2. × 3 повтора = ~45 прогонов.
**Quality (7B):** 5 × 3 = 15.
**Debug (1.5B):** ~8–10 × 1.
→ один ночной прогон (~6–9 ч).

## 8. Порядок реализации (база — `rollback-pr2`; `main` = референс механик)
`main` ушёл «не туда» по фокусу, но проверенные механики берём оттуда референсом (не структуру). **Карта переиспользования:**
- bnb-квант ← `main:scripts/benchmark_quant.py`
- perplexity + WikiText ← `main:src/llm_inference/quality.py`, `main:scripts/eval_quality.py`
- повторы/variance, тайминги ← `main:src/llm_inference/{runner,timing,summary}.py`
- драйвер матрицы (процесс-на-конфиг) ← `main:scripts/run_matrix.py`
- *(опц.)* roofline/MBU ← `main:scripts/roofline.py`

**Шаги:**
1. **Порт механик** в простой стиль rollback-pr2: лёгкий общий модуль + единый `benchmark.py` (flags), повторы/variance, perplexity, bnb-квант. Сверить с baseline/manual_kv.
2. **Fixed-length, метаданные (git/temp/clock), дамп текста.**
3. **AWQ/GPTQ** (новое).
4. **Спек-декодинг** + правка стримера (acceptance rate); **fidelity == fp16**.
5. **Батчинг** (left-pad, агрегатные метрики) + batch-sweep.
6. **Комбинации** (int4+spec, AWQ+spec).
7. **Драйвер** (порт run_matrix) + агрегатор `aggregate.py` + **MMLU/GSM8K** (новое в quality, рядом с perplexity).
8. **Графики** `plots.py` по методам.
9. Полная отладка на 1.5B → запуск 7B на ночь (квант batch-sweep и точки кэша добираем в ту же сессию).

## 9. Зависимости и загрузки (ставлю только после ОК)
- `bitsandbytes`, эвалюатор качества (`lm-eval` или свой), `matplotlib`/`pandas`, для AWQ/GPTQ — соответствующие бэкенды (`autoawq`/`auto-gptq` или встроенная поддержка transformers).
- Загрузки: `Qwen2.5-7B-Instruct` (~15GB) + `Qwen2.5-0.5B-Instruct` (~1GB) + AWQ/GPTQ-чекпойнты 7B. Проверю место на диске.

## 10. Риски
- Скачивание/прогон 7B — если не успеть, всё опирается на 1.5B (самодостаточно), 7B бонусом.
- AWQ/GPTQ-чекпойнт для 1.5B может отсутствовать → на 1.5B только bnb.
- lm-eval vs transformers 5.8 → fallback свой эвалюатор.
- Тепловой дрейф на длинном прогоне → чередование + лог клоков.
- bnb на маленькой модели не ускоряет (только память) — идёт в выводы.
